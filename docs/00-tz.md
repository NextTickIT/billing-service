# ТЗ: Собственный платёжный шлюз


---

## 1. Зачем мы это делаем

Сегодня подписки живут на связке WayForPay (карточные рекурренты) + SendPulse (бот, CRM, статус подписки).
Эта связка порождает две системные проблемы:

1. **Пользователь получает «ты не оплатил» после успешной оплаты.** WayForPay успешно списывает
   рекуррентный платёж, но SendPulse узнаёт об этом с непредсказуемой задержкой (а в 247
   зафиксированных случаях — не узнал вовсе). Автоматизации бота тем временем шлют человеку
   предупреждения о неоплате. Это за пределами нашего контроля, пока состоянием владеет чужая связка.
2. **Рекуррентами управляет WayForPay, а не мы.** Регулярные платежи заведены на стороне провайдера:
   мы не выбираем расписание ретраев, не видим дату отмены, не можем перенести пользователя
   на другой процессинг. Токен карты принадлежит провайдеру, а не нам.

Шлюз забирает себе **деньги и биллинг-цикл** и рассылает всем заинтересованным системам события
о платежах **раньше, чем штатные автоматизации успевают ошибиться**.

## 2. Что шлюз ЕСТЬ и чем он НЕ является

**Шлюз — это:**
- оркестратор оплат продления (checkout-страница);
- владелец собственного биллинг-цикла: токен карты, дата следующего списания, ретраи;
- единая точка приёма платёжных событий из любых источников;
- издатель событий «оплата прошла / не прошла» для внешних систем.

**Шлюз — это НЕ:**
- НЕ владелец подписочной логики. «До какой даты у человека доступ», «на сколько дней продлить» —
  решает внешняя система (сегодня SendPulse). Шлюз сообщает факты о деньгах, внешняя система
  распоряжается доступом.
- НЕ владелец идентичности (та что identity). Шлюз принимает непрозрачный `external_user_id` от вызывающей системы
  и возвращает его во всех событиях без трансформаций. Никакого матчинга людей по email/телефону
  внутри шлюза нет и не будет 
- НЕ CRM, НЕ бот, НЕ аналитика.

## 3. Ключевой принцип: всё внешнее — заменяемый коннектор

WayForPay, Whitepay, SendPulse — детали реализации. Ядро шлюза общается с внешним миром только
через два вида коннекторов:

| Вид | Обязанности | Первые реализации |
|-----|-------------|-------------------|
| **Коннектор платёжного провайдера** | создать оплату; токенизировать карту; списать по токену; разобрать вебхук провайдера в стандартное платёжное событие | WayForPay (карты, токенизация), Whitepay (крипта) |
| **Коннектор синхронизации (sink)** | доставить исходящее событие шлюза во внешнюю систему | SendPulse (обновление состояния подписки/переменных) |

Требование заменяемости — проверяемое: добавление нового провайдера или нового sink-а
не должно требовать изменений ядра (см. критерий приёмки AC8).

## 4. Основные сущности

| Сущность | Что хранит | Кто владеет |
|----------|-----------|-------------|
| Подписка шлюза | `external_user_id`, сумма, период, дата следующего списания, состояние ретраев, ссылка на токен карты | шлюз |
| Токен карты | платёжный токен провайдера, маска карты | шлюз (сам токен — у провайдера, но управляем мы) |
| Checkout-сессия | `external_user_id`, сумма, период, выбранный метод | шлюз |
| Платёжное событие (входящее) | источник, ключ идемпотентности, сумма, статус, сырой payload | шлюз |
| Исходящее событие | тип, `external_user_id`, детали платежа, сырой payload | шлюз, доставляется sink-ами |
| Карантинная очередь | неопознанные входящие события + решения оператора | шлюз |
| Подписка/доступ пользователя | paid_till, статус доступа | **внешняя система** (SendPulse) |

## 5. Сценарии

### Сценарий 1. Ручное продление через checkout

1. Внешняя система (бот) создаёт checkout-сессию: `external_user_id`, сумма, период — и получает ссылку.
2. Пользователь открывает страницу. Страница **минимальна**: выбор способа оплаты (карта / крипта)
   и кнопка оплаты. Никакого paid_till на странице нет — дату показывает бот
   (решение интервью: не тянуть дату из системы, которая сама лагает).
3. Пользователь платит у провайдера. Для карты — с токенизацией: токен сохраняется у нас.
4. Провайдер присылает вебхук об успехе → шлюз фиксирует платёж, **создаёт/продлевает подписку шлюза**
   (сумма и период берутся из checkout-сессии; следующее списание = дата оплаты + период)
   и публикует событие `payment_succeeded` наружу.
5. Sink-коннектор доставляет событие в SendPulse **не позднее 60 секунд** после фиксации платежа.

### Сценарий 2. Входящие рекуррентные события извне

У шлюза может быть много источников, сообщающих «рекуррентный платёж списан/не списан»:

- вебхуки провайдеров, где callback направлен на нас;
- **миграционный поллер WayForPay** (см. §7): для 500+ существующих рекуррентов callback-url
  сменить нельзя, поэтому отдельный сервис каждые несколько минут читает журнал операций W4P
  и превращает найденные платежи в стандартные входящие события шлюза;
- любые будущие источники.

Все источники равноправны: событие проходит один и тот же путь —
сырой лог → идемпотентность → привязка к подписке → исходящее событие наружу.

### Сценарий 3. Собственный биллинг-цикл

1. Наступает дата списания подписки шлюза → шлюз списывает сумму по хранимому токену через
   коннектор провайдера.
2. Успех → сдвиг даты следующего списания на период подписки, событие `payment_succeeded` наружу.
3. Неудача → ретраи по фиксированному расписанию: **дни 0, 1, 3, 5, 7** от первой неудачи.
   - Каждая неудачная попытка публикует событие `charge_retry_failed` (внешняя система сама решает,
     писать ли человеку «пополните карту»).
   - Неудача попытки 7-го дня — финальная: событие `renewal_failed`. Дальше шлюз ничего не делает
     с этой подпиской, судьбу доступа решает внешняя система.

### Сценарий 4. Неопознанный платёж → карантин

Если входящее событие не матчится ни с одной подпиской или checkout-сессией
(платёж по до-шлюзовому рекурренту, кривой референс и т.п.):

1. Событие в любом случае сохранено в сыром виде.
2. Попадает в карантинную очередь; оператор получает алерт.
3. Оператор вручную привязывает событие к подписке (или заводит подписку) — после привязки событие
   **допроцессируется штатно**, как будто пришло привязанным (включая исходящие события).
4. Целевая метрика: **ноль навсегда-непривязанных платежей** (в текущей системе их 646).

## 6. Исходящие события

Минимальный словарь (расширяемый):

| Событие | Когда | Обязательные поля |
|---------|-------|-------------------|
| `payment_succeeded` | зафиксирован успешный платёж (checkout, свой биллинг, внешний источник) | external_user_id, сумма, валюта, метод, период, источник |
| `charge_retry_failed` | неудачная промежуточная попытка списания | external_user_id, номер попытки, дата следующей попытки, причина провайдера |
| `renewal_failed` | финальная неудача цикла ретраев | external_user_id, причина |
| `subscription_created` | появилась новая подписка шлюза | external_user_id, сумма, период |
| `subscription_cancelled` | подписка остановлена (оператором/по событию провайдера) | external_user_id, причина |
| `unknown_payment_quarantined` | событие ушло в карантин | ссылка на карантинную запись |

Гарантии доставки: каждое событие доставляется в каждый подключённый sink **хотя бы один раз**;
sink-коннектор обязан быть идемпотентным на своей стороне. Неудачная доставка ретраится;
недоставленные события видны оператору.

## 7. Миграция с WayForPay-рекуррентов

Факты: токены карт 500+ действующих рекуррентов принадлежат W4P и наружу не выдаются;
callback-url аккаунта сменить нельзя. Следствие: **миграция возможна только действием пользователя**
(переввод карты через наш checkout), и хвост старых рекуррентов может жить годами.

Стратегия «гибрид»:

- **Мягко ведём**: при каждом касании пользователя (продление, сбой списания, общение с ботом)
  внешние системы предлагают перепривязать карту через наш checkout. В частности, при сбое
  списания старого рекуррента вместо надежды на ретраи W4P человека зовут оплатить по-новому.
- **Не форсируем**: принудительной отмены старых рекуррентов нет.
- **Поллер — полноценный долгоживущий компонент**, а не времянка: с мониторингом, алертами
  и **метрикой убывания хвоста** немигрировавших (видимой оператору).
- Лаг поллера = интервал опроса журнала W4P (минуты); SLA «≤ 60 секунд» отсчитывается от момента,
  когда шлюз узнал о платеже.

## 8. Industrial grade: обязательные свойства

Это система про деньги. Не обсуждается:

1. **Сырой журнал всего.** Каждое входящее событие (вебхук, ответ провайдера, находка поллера)
   и каждое исходящее событие сохраняются в неизменяемом сыром виде (append-only) до любой обработки.
   По журналу можно доверенно восстановить состояние любой подписки и разобрать любой инцидент.
2. **Идемпотентность.** Вебхуки доставляются at-least-once: повторная доставка того же события
   (по ключу идемпотентности источника) не создаёт ни второго платежа, ни повторных исходящих событий.
3. **Терпимость к чужим контрактам.** Провайдеры врут о форматах. Разбор входящих данных не должен терять событие целиком
   из-за одного неожиданного поля: сырое всегда сохранено, проблемное — в карантин, а не в /dev/null.
4. **Деньги и время.** Суммы — только целые минимальные единицы валюты; все временные метки — UTC.
5. **Наблюдаемость.** Оператор видит: очередь карантина, недоставленные исходящие события,
   подписки в ретраях, свежесть поллера, хвост миграции. На каждую из этих очередей есть алерты.
6. **Аудит ручных действий.** Каждая ручная привязка/правка оператора фиксируется: кто, когда, что.

## 9. Критерии приёмки

- [ ] **AC1.** После успешного списания (вебхук или поллер) внешняя система обновлена ≤ 60 сек.
      Проверка боли №1: бот более не отправляет «ты не оплатил» после успешного списания.
- [ ] **AC2.** Повторная доставка того же вебхука не создаёт ни дублей платежа, ни повторных исходящих событий.
- [ ] **AC3.** Каждое событие доступно в сыром виде; состояние любой подписки восстановимо реплеем журнала.
- [ ] **AC4.** Ретраи списания идут по расписанию 0/1/3/5/7 дней; на 7-й день — финальное `renewal_failed`;
      каждая неудача видна как событие.
- [ ] **AC5.** Checkout: по ссылке с `external_user_id` пользователь выбирает метод и платит; успех рождает
      подписку шлюза и событие наружу; для карты сохранён токен.
- [ ] **AC6.** Неопознанный платёж попадает в карантин с алертом; после ручной привязки допроцессируется
      штатно; счётчик «навсегда-непривязанных» = 0.
- [ ] **AC7.** Платежи немигрировавших W4P-пользователей появляются как стандартные события с лагом
      ≤ интервала опроса; метрика хвоста миграции доступна оператору.
- [ ] **AC8.** Новый провайдер или новый sink подключается без изменений ядра — только новый коннектор.
- [ ] **AC9.** Все исходящие события несут `external_user_id` без трансформаций.

## 10. Вне рамок (non-goals)

- Identity resolution (матчинг людей между системами).
- Логика доступа: paid_till, grace доступа, «на сколько продлить» — внешняя система.
- Справочник тарифов внутри шлюза (сумма+период приходят при создании подписки).
- Показ paid_till на checkout-странице.
- Аналитика и витрины (остаются в существующей системе; шлюз даёт им честный поток событий).
- Замена SendPulse как CRM/бота.

## 11. Открытые вопросы (решить до реализации)

1. **Возвраты (refund):** проходят ли через шлюз, событие `payment_refunded` и его влияние на подписку.
2. **Смена карты активной подписки** без сбоя списания (пользователь сам хочет обновить карту).
3. **Отмена подписки пользователем:** через какой канал (бот → API шлюза?) и что происходит с датой списания.
4. **Валюты:** сегодня USD/UAH; фиксируется ли валюта подписки навсегда при создании.
5. **Несколько подписок на одного `external_user_id`:** разрешено или одна активная (делаем сразу "несколько продуктов"?).
6. **Безопасность checkout-ссылок:** срок жизни сессии, защита от подбора, кто вправе создавать сессии.
7. **Права и границы оператора карантина** (кто может привязывать платежи и отменять подписки).
